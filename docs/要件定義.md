# 要件定義

- プロジェクト名: 可能性ラボ 集客〜コーチング運用システム（リポジトリ名 `resiteLP` / Vercel `kanousei-labo`）
- 最終更新: 2026-08-10
- 状態: **下書き（v0.2）**。`【要確認】` は木戸さんに確認して埋める箇所。
- 関連: 実装状況は [機能要項.md](機能要項.md)、過去に踏んだ失敗は [開発規則.md](開発規則.md) の R-番号。

このリポジトリには LP群・職業タイプ診断・候補者マイページ・管理アプリが同居している。
バラバラの4サイトではなく、**1本のファネルを支える1つの道具**として書く。

---

## 1. 何のための道具か

> **コーチが「あの候補者、今どこまで進んでたっけ」を探す時間を無くす。**

候補者は LINE・診断結果・予約フォーム・面談メモと、情報が置かれる場所がバラバラになる。
コーチが持つべき答えは常に1つ「この人は今どのステージで、次に何をするか」。
それを**1画面で出す**ことがこの道具の存在理由。

補助的な目的として、LP・診断は「LINE友だち追加」という単一のゴールに candidate を流し込む入口である。
入口を増やすことではなく、**入口を1本に絞ったまま取りこぼさないこと**が要件。

## 2. 誰が使うか

| 使う人 | 端末 | 1日に何回触るか | この人にとっての「これがあれば嬉しい」 |
|---|---|---|---|
| **コーチ 2〜3名**（主役） | PC・スマホ両方（同程度） | **10〜30回** | 移動中にスマホで次の面談相手の状況が読める。面談直後にその場でメモを残せる |
| 運営（木戸さん） | PC中心 | 数回 | 全体のファネルが1枚で見える。お知らせを全員に一括で出せる |
| 候補者（20〜30代の転職検討層・学生） | **ほぼスマホ** | 週1回未満 | LINEから飛んで、自分の予約と次回テーマがログイン無しで見える |

### 操作回数からくる設計制約（機能を作る前にここを見る）

コーチが1日10〜30回触り、その半分がスマホ。つまり：

- **1操作＝3タップ以内**で終わること。ステージ変更・面談メモ追記のような毎日やる操作は特に。
- **スマホで完結すること。** 「これはPCでやってください」を作った時点でその機能は使われない。
- 毎回同じ値を入れる欄は**初期値を入れておく**（コーチ名、面談種別、次回日時の候補）。
- 一覧は**探さずに目に入る**こと。検索してから見つけるのは10回/日には耐えない。

`【要確認】` コーチ2〜3名は**互いの担当候補者を見てよいか**。
見せない方針なら権限分離が必要になり、設計が一段重くなる。現状の実装は全員が全件見える前提。

## 4. やらないこと（スコープ外）

**このセクションが一番大事。** ここが空だと何でも作ることになる。

| やらないこと | なぜ／いつなら考えるか |
|---|---|
| **Stripe 等のオンライン決済の自動化** | 体験完了→コーチング中のゲート。運用担当が未定なので、当面は「誰でも手で入金確認して記録する」形。担当が決まったら Payment Link を後付けする |
| **コーチ間の権限分離（担当外を見せない）** | 2〜3名の相互信頼で回る規模。人数が増えるか、見せたくない情報が出たときに考える |
| **カンバンのドラッグ&ドロップ** | v1はカード上のセレクトで変更。スマホ半分の運用でD&Dは事故る。PC専用機能を作らない方針（実装されていないことを確認済み） |
| **SMS・メールの自動送信** | 連絡はLINEに一本化。予約完了の案内も「担当コーチから連絡する」運用にした（R-002） |
| **お知らせのCTAボタン** | 遷移先を保存する列が無く、押しても動かないダミーだったため撤去。`announcements.cta_url` を足すときに再検討 |
| **メール通知・メールアドレスの収集** | 連絡は LINE に一本化済み。DBにも `email` は持っていない。二重の連絡経路を作らない |
| **人材紹介（送客）フェーズの管理** | 「完了」以降の別レイヤー。コーチングが安定して回ってから |
| **GA4 連携／診断結果・図鑑のOGP画像** | やる価値はあるが集客の伸びが先。GTM側の設定で後から足せる |
| **実績数字（92%等）・コーチ一覧のLP掲載** | 数字が未確定のため2026-07-02に削除済み。**Git履歴に残っており復活可**。裏付けが取れたら戻す |
| **管理アプリのオフライン対応・PWA化** | 面談は基本オンライン（Zoom）で電波のある場所。必要になってから |
| **旧 `booking/` ディレクトリ・Netlify Forms** | 撤去済み。README に記述が残っているが**現状と乖離しているので参照しない**（README要更新） |

## 5. 守らなければならないこと（非機能）

### 個人情報
- **持っているもの**: 氏名 `name`、電話番号 `phone`、年齢帯、居住地、経験、面談メモ、コーチング記録（`candidates` / `appointments` テーブル）。
- **持っていないもの**: メールアドレス、住所、決済情報。**意図的に持たない。**
- 通信は Vercel / Supabase とも HTTPS。この条件を満たすので本番に個人情報を置いてよい。
- マイページは `reservation_token`（32桁hex）だけでアクセスできる = **URLを知る＝本人**とみなす設計。
  トークンが漏れたら他人にも見える。`【要確認】` 有効期限・再発行の運用を決めるか、決めずに受け入れるか。
- コーチ行動規範上、**個人情報の外部共有は禁止**。スクショをLINEグループに貼るような運用を作らない。

### 止まったら困る度合い
- **1時間止まると**: 新規の無料体験予約が取れない（機会損失）。面談中ならメモが残せない。
- 致命的ではないが、**予約フォームが落ちる＝広告費が無駄になる**。LP → LINE の導線は静的HTMLなので Supabase が落ちても生きる（これは意図した冗長性）。

### 同時に使う人数
- 運用側は最大3〜4名。候補者側は同時数名程度。**スケールは要件ではない。**

### データを失ったら
- 失うと復旧できないのは**面談メモとコーチング記録**（コーチの頭の中にしかない情報）。
- 候補者の基本情報は LINE のやり取りから復元可能。診断結果は再受験できる。
- `【要確認】` Supabase のバックアップ方針が未確認。無料プランだと Point-in-Time Recovery が無い。
  **最低限、コーチング記録の定期エクスポートは要る。** 未実装。

## 6. 用語

現場で使われている言葉をそのまま書く。**AIが勝手に言い換えないための表。**

| 言葉 | 意味 |
|---|---|
| 候補者 | サービスを受ける人。「ユーザー」「顧客」「クライアント」と言い換えない |
| ステージ | 候補者が今いる段階。`無料体験予約 / 体験完了 / コーチング中 / 完了 / 見送り` の5つだけ |
| 無料体験 | 初回の面談。「カウンセリング」「初回面談」ではなくこの呼び方 |
| 見送り | 離脱。本線4段から外れる。「失注」「NG」と書かない |
| セグメント | `career`（中途）/ `newgrad`（学生・インターン）の2つ |
| 職業タイプ / 16タイプ | 診断の結果。4軸×2極の4文字コード（例 `ETOP`） |
| 連携コード | 診断結果を候補者プロファイルに紐付けるためのコード。LINEで送付する |
| プロファイル | 候補者1人の詳細画面。基本情報 / 第一面談 / 第二面談 / 適性テスト / 総合所見 / 送客判断 / コーチング / マイページ の**8タブ** |
| スタンダード / フル | 料金プラン。¥80,000（1ヶ月・全4回）/ ¥150,000（2ヶ月・全8回）。**この2つが正**（マニュアルの¥50,000/¥100,000は旧） |
| お知らせ | マイページに出す通知。**共通**（全員）と**個別**（その候補者だけ）がある |
| 可能性ラボ / 可能性LABO | サービス名。表記ゆれあり。`【要確認】` どちらを正とするか |

## 7. 前提・制約

- **使う技術**: 静的HTML/CSS/JS（LP・診断・マイページ）、Vite + React 18 + TypeScript（`app/`）、Supabase（Postgres + Auth + RPC）。ビルド不要の面はビルドしない方針。
- **動かす場所**: Vercel 単一プロジェクト `kanousei-labo`（本番 https://kanousei-labo.vercel.app ）。
  ルート `vercel.json` → `scripts/build-vercel.mjs` が `STATIC_SITES = [mypage, type-test, intern, mid-career]` を `dist` へコピーし、`app/` を Vite ビルド。
- **Supabase**: project ref `rygredsfgbvjtllnlrto`。RPC: `mypage_get` / `mypage_book` / `book_trial` / `mypage_announcements` / `slot_counts`。
  マイグレーションは `app/supabase/migrations/0001〜0005`。
  **⚠️ 未適用が2件あります**（どちらも Supabase SQL Editor に貼って実行が必要）:
  - `0004_mypage_content.sql` … マイページ管理機能（コーチメッセージ・お知らせ）が動かない
  - `0005_slot_availability.sql` … **二重予約が止まらない**。適用するまで全枠が「空き」に見える
- **開発環境**: VPS `manaki@160.251.211.226`（Ubuntu 24.04 / RAM 2GB / Node は nvm v24）。Windows と VPS の両方から作業する。
- **記憶の引き継ぎ**: Obsidian Vault は `obsidian/`（別リポジトリ）。ルールは ルート `CLAUDE.md`。
- **予算・期限**: `【要確認】` 未確認。
- **既にあるもの**: 上記すべて実装済み・デプロイ済み。**新規開発ではなく、動いているものへの追加・修正**が今後の作業。
