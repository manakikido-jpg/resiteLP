# 開発規則

守るべきことを `R-番号` で記録する。

**バグを踏んだら必ずここに残す。直して終わりにしない。**
書くのは次の3つ。これが揃っていないものは規則にならない。

1. **何が起きたか**（利用者から見て何が困ったか）
2. **なぜそうなったか**（表面の症状ではなく、本当の原因）
3. **今後どうするか**（次に同じ場面が来たとき、何を守るか）

一度振った番号は変えない。コメントやコミットメッセージから参照するため。

---

## 書き方の例

実際のプロジェクトから。この粒度で書けば役に立つ。

- **R-539 `backdrop-filter` を付けた要素は `position: fixed` の基準になる**:
  ヘッダーに `backdrop-filter` を付けていたため、その中の引き出しメニューが
  **ヘッダーの高さに閉じ込められて開かなかった**。
  画面全体に広げたい要素は `createPortal` で `document.body` の直下に出す。

- **R-563 画面下に固定して浮かせる要素は、必ず何かを塞ぐ**:
  「ホーム画面に追加」の案内を `fixed bottom-*` で出したところ、
  下部タブと送信ボタンに覆いかぶさり**押せなくなった**。
  位置を上にずらしても別のボタンを塞ぐだけだった。
  案内は**通常の要素として本文に流し込む**。浮かせない。
  検証では、ボタンの中心に本当にそのボタンがあるかまで確かめる。
  「表示されている」だけでは押せるとは限らない。

- **R-564 検証で邪魔な要素を消してはいけない**:
  通し検証のとき案内カードを消してから操作していたため、
  それがボタンを塞いでいることに気づけなかった。
  **利用者が最初に見る状態のまま**試すこと。

> 3つとも「画面が崩れた」で片付けられた話です。
> 原因まで書いてあるから、次に同じ場面で止まれます。

## 規則

- **R-001 「今日」をモジュール定数に固定しない**:
  スケジュール画面の基準日が `const SCHED_TODAY = new Date(2026, 5, 3)` のまま本番に出ており、
  コーチが開くと**常に2026年6月が表示され、「今日」ボタンも6月3日に飛んでいた**。
  同じ固定値が時間枠設定（`FORM_TODAY`）にもあり、「休止日を追加」を押すたび**過去日が入っていた**。
  デモ用に置いた固定日が、そのまま本番の基準になっていたのが原因。
  日時の基準は**必ず呼び出しのたびに `new Date()` から取る**。
  モジュールのトップレベルに `new Date(...)` を書かない。既定値の配列（休止日など）にも日付を埋めない。
  デモ用の値を置くときは、`import.meta.env` などで**本番と分岐できる形にしてから**置く。

- **R-002 実装していないことを画面に書かない**:
  予約完了画面に「確認SMSと、Zoomリンクを記載したメールを送信しました。」と出していたが、
  **送信の実装はどこにも無く、DBにメールアドレスの列すら無い**。
  マイページにも「参加する」「カレンダーに追加」「市場価値診断」など、
  押すとトーストが出るだけで**何も起きないボタン**が並んでいた（「カレンダーに追加しました」と嘘の完了通知まで出していた）。
  プロトタイプの見た目をそのまま本番に持ち込み、中身の実装だけが抜けたのが原因。
  **画面に書いてよいのは、実際に起きることだけ。**
  実装が無い機能は、ダミーで置かずに**消す**。消せない事情があるなら「〜します」ではなく
  「〜は担当コーチからご連絡します」のように、**誰が何をするかを事実として書く**。
  「押したら何が起きるか」を説明できないボタンは、その時点で出してはいけない。

  **2026-08-10 追記（LP側でも同じものが見つかった）**:
  中途LPの「次へすすむ」ボタンには `onclick` が最初から無く、**押しても何も起きなかった**。
  しかも回答を選ぶと `.ok` が付いてボタンが光るため、**押せると思わせて反応しない**状態だった。
  学生LPには付いていたので、片方だけ付け忘れたまま本番に出ていたことになる。
  検証で見落とした原因は、私のテストが `a[href*="lin.ee"]` を対象にしていて、
  **このボタンはその条件に当てはまらなかった**こと。
  → CTAの検証は「LINEに繋がる要素」ではなく、**押せる要素すべて**を対象にする。

- **R-003 DB既定値を持つ列に null を明示送信しない**:
  `candidates.reservation_token` は `default encode(gen_random_bytes(16),'hex')` を持つのに、
  upsert が `reservation_token: c.reservationToken ?? null` と**null を明示送信して既定値を潰していた**。
  結果、管理アプリで手動追加した候補者は**永久にマイページのリンクを発行できなかった**。
  DBの既定値は「列を省いたとき」にしか効かない。
  値を持たないなら**列ごとオブジェクトから外す**。`?? null` で埋めない。
  加えて、リンクが出せない候補者に対しては**ボタンを隠して終わりにせず、その場で発行できる導線**を用意する。

- **R-004 本番に「押すとデータが増えるデモ」を置かない**:
  スケジュール画面に常設された「フォーム連携をデモ」ボタンが、
  押すと架空の候補者「藤井 結衣（090-7777-1234）」を**本番Supabaseに実登録**していた。確認ダイアログも無し。
  ローカル検証用の導線を、環境で分岐させないまま本番に出したのが原因。
  データを作る・消す操作は、**環境で出し分ける**か、**取り消せることを確認したうえで確認ダイアログを付ける**。
  「デモ」という名前は、押す人にとって安全性の保証にならない。

- **R-005 氏名を姓と名に分割して表示しない**:
  マイページのあいさつが `ME.name.split(" ")[1]` で「名」だけを出していたため、
  スペース無しで登録された候補者は**氏名が丸ごと消えて「こんにちは、さん」**になっていた。
  デモデータが「山本 さくら」とスペース入りだったので開発中は一度も露見しなかった。
  氏名は**自由入力の1項目**として扱い、分割しない。
  表示の検証には**スペースを含まない名前**を必ず1件混ぜる。

- **R-006 サイト内リンクは統合ビルド後のパスで確認する**:
  公開予約ページのロゴと「← トップへ」が `/` を指していたが、
  統合ビルドでは `/` が**管理アプリのログイン画面**になるため、候補者が社内画面に着いていた。
  各サイトを単体で作ってから1つのVercelプロジェクトに集約したので、開発時のパス感覚とズレたのが原因。
  リンク先は `dist/` を組んだ状態で開いて確かめる。ルート（`/`）を「トップページ」と仮定しない。

- **R-007 「表示で防ぐ」は防止策にならない。可否はサーバで強制する**:
  公開予約ページは既存予定を読んで満枠を伏せる作りだったが、匿名ロールには
  `appointments` の SELECT 権が無いため**常に0件が返り、全時間帯が「空き」に見えていた**。
  マイページ側は全枠 `taken: false` を返し、コメントには「capacity判定はサーバ側」と
  書いてあったのに、`book_trial` / `mypage_book` のどちらにも定員チェックが無かった。
  **「クライアントが弾いてくれる」前提でサーバのチェックを省いた**のが原因。
  加えて、権限の都合でクライアントがデータを読めていないことに誰も気づけなかった。
  予約・在庫・重複のような**取り合いになる判定は必ずサーバ側で強制する**。
  画面の制御は「選ばせない親切」であって、防止策ではない。
  同時実行も想定し、枠単位のロック（`pg_advisory_xact_lock`）で直列化する。
  そして**匿名に見せてよいのは件数だけ**。氏名や電話を含むテーブルを読ませて解決しない。
  なお、コメントが「サーバ側でやっている」と書いているときは**本当にやっているか確かめる**。
  このコメントは3ヶ月間、誰も疑わなかった。

- **R-008 手で適用するSQLは、事前に本物のPostgresで流して確かめる**:
  migration はユーザーが Supabase の SQL Editor に貼って実行する運用なので、
  構文エラーや権限ミスがあると、その場で止まって原因も分かりにくい。
  0005 は Docker の `postgres:16-alpine` に 0001〜0005 を順に適用し、
  定員超過・過去日時・不正な日時・キャンセル後の復活・同時8並列・
  匿名からの直読み拒否まで**実際に流して**から渡した。
  ローカルに無い Supabase 固有のもの（`pgcrypto`、`anon` / `authenticated` ロール）は
  前置きSQLで補えば再現できる。

- **R-009 デプロイの「Building…」が長いときは、遅いのではなく止められている可能性を先に疑う**:
  `vercel --prod` が延々と `Building…` を表示し続けた。実際には**Vercelが最初から展開を拒否**しており、
  ビルドは1秒も走っていなかった。理由は
  **コミットのメールアドレス（`aisiro1644@gmail.com`）が、Vercelアカウントに紐づく
  GitHubアカウントのメール（`manaki.kido@gmail.com`）と一致しなかったため**。
  CLIの表示では「処理中」と「拒否された」が見分けられず、
  ダッシュボードの該当デプロイを開くまで分からなかった。

  **今後どうするか**:
  1. **コミットのメールは、デプロイ先アカウントのメールに揃える**。
     複数の環境（Windows / VPS）から作業するときは、両方で `git config user.email` を確認する。
  2. デプロイが2〜3分で終わらないときは「遅い」と解釈せず、
     **まずダッシュボードの該当デプロイを開いて状態を見る**。`Building` `Queued` `Error`
     `ブロックされました` のどれなのかを確認してから手を打つ。
  3. **失敗の可能性を潰す前に最適化しない。**
     このとき私は原因を「ビルドが重い」と決めつけ、`.vercelignore` の追加と
     `npm install → npm ci` の変更に時間を使った。どちらも有用ではあったが、
     **本当の原因とは無関係**で、その間ずっとデプロイは止まったままだった。
     症状から原因を推測する前に、**まず事実（ログ・状態）を取りに行く**。

- **R-010 フォントのウェイトは「実際に描画に使われている組み合わせ」から決める**:
  LPが読み込む書体定義CSSが **1,132KB** あり、ページ最大の重量物になっていた。
  日本語書体は1ウェイトあたり `unicode-range` が100ブロック超あるため、
  ウェイトを1つ足すだけでCSSが数十KB増える。
  実態は「4書体18ウェイト」で、そのうち **Inter は一度も使われておらず**、
  **font-weight:800 はCSSに1箇所も無い**のに読み込んでいた。

  **今後どうするか**:
  1. 削る前に、ブラウザで全要素の `getComputedStyle` を走査し、
     **(書体, ウェイト) の実使用の組み合わせ**を出す。CSSのgrepでは
     継承や擬似要素を追えず、判断を誤る。
  2. 外すウェイトを使っている要素は、**こちらで明示的に残すウェイトへ寄せる**。
     ブラウザ任せにすると近いウェイトが自動で選ばれ、意図しない見た目になる。
  3. 変更後はスクリーンショットで見た目が変わっていないことを確認する。

  結果は 1,132KB → 675KB（-40%）。
